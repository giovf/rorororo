## 7. Proposals

**1. Enforce the RUNS.md 120-char cap in `npm run check`, not just in the header text.**
Evidence: 269 of 304 lines this week (88%) exceed the file's own stated limit (§4); the rule
has existed since the file's creation (2026-09-22) and has never once been machine-checked.
Fix: a small script (same shape as `scripts/handoffs.ts`/`scripts/slot.ts`) that reads the
lines added to `docs/RUNS.md` in the current push's diff range and fails if any exceeds 120
characters after the `| <routine> | ` prefix, wired into `npm run check`; add one sentence to
each routine's `docs/routines/<name>.md` noting the check exists, so a routine that trips it
once learns to split long lines into two. `effort_days`: 0.15. `proof`: zero RUNS.md lines
over 120 chars added in the next 30 days; `npm run check` fails locally on a violation.
Evidence 3 (88% violation, 2 weeks unnoticed) × reach 3 (every routine that writes RUNS.md) ÷
0.15 days. **Score: 7.**

**2. Widen the refresh-error queue rule from "two consecutive days" to a rolling window.**
Evidence: `uk-insolvency` broke the consecutive-day pattern on purpose by alternating
(09-28/29/30 error, 10-01 clean, 10-02 error again) even after a dedicated fix landed
(`refresh-uk-insolvency`, done 09-30) — the mechanism built specifically to catch exactly this
kind of recurring error (`refresh-errors-to-queue`) cannot see an every-other-day flake by
construction. Fix: `ventures/gankdat/scripts/refresh-errors-to-queue.ts` compares today's
error slugs against the last 4 Daily-numbers rows (not just yesterday) and files/extends the
item when a slug appears in ≥ 2 of them, still idempotent and still cooling off 14 days once
done. `effort_days`: 0.1. `proof`: an every-other-day flaky source gets queued within 4 days
instead of never; `uk-insolvency` specifically gets re-queued on its next error under the new
rule. Evidence 3 (recurred after its own dedicated fix) × reach 3 (all 17 gankdat sources,
every day) ÷ 0.1 days. **Score: 7.**

**3. A billing/usage alert above the LEDGER.md baseline always gets an owner line, never just "logged".**
Evidence: the 2026-10-01 17:55 Cloudflare metered-usage alert ($15.00, 20 days into a 30-day
period, against the £3.70/mo baseline in `docs/LEDGER.md`) was triaged as plain `logged` — no
`owner:` line, no ledger note — because `docs/ops/SELF-CAUSED.md`'s table only names
deploy-confirmation mail for Cloudflare, not cost alerts, so the triage prompt had no branch
for it. Fix: one sentence in `docs/routines/inbox-triage.md`: "A billing or usage alert from a
paid service (Cloudflare, Chrome Web Store, domain registrar, …) that names a figure above the
line it has in `docs/LEDGER.md` is never `logged` alone — add an `owner:` line in ALERTS.md
naming the service, the reported figure and the LEDGER.md baseline it exceeds, and leave a
`<!-- unconfirmed -->` note on that LEDGER.md row for the next reconciliation." `effort_days`:
0.05. `proof`: the next billing alert above its LEDGER.md baseline gets an `owner:` line and a
LEDGER.md note the same day. Evidence 2 (one occurrence, but a real near-miss against the
£100 cap) × reach 2 (every paid service's billing mail, every triage run) ÷ 0.05 days. **Score: 6.**

**4. Ops retro gains a step to unshallow its clone before trusting `git log --since`.**
Evidence: this very run's sandbox clone was shallow at ≈54 commits (`git rev-parse
--is-shallow-repository` → true), which only reached back to 2026-10-01T00:35 — about 2 of
the 8 days this routine is told to measure. `git fetch --unshallow origin` fixed it, but
nothing in `docs/routines/ops-retro.md` says to check. At this repo's current pace (~50-60
commits/week) any default shallow-clone depth will keep cutting the window short for exactly
this routine, every week, silently (a short `git log` doesn't error, it just under-counts).
Fix: add one step to `docs/routines/ops-retro.md`, right after the initial checkout: "if `git
log --since='8 days ago' --format=%cI | tail -1` is less than 7 days old, run `git fetch
--unshallow origin` (or `--deepen=200` if unshallow fails) before measuring anything below."
`effort_days`: 0.05. `proof`: the next retro's git log genuinely spans the full 7-8 day window
(spot-checked: oldest line ≥ 7 days old) without a manual unshallow. Evidence 2 (this run hit
it directly) × reach 2 (every future weekly retro) ÷ 0.05 days. **Score: 6.**
