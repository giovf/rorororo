# Work pipeline — the exchange and the venture queues

Owner decision 2026-09-22: work is organised as a hierarchy of queues. **`queues/foundry.json` is the
operation's own queue** (owner 2026-09-24: self-expansion — routines, relays, watchdogs, retros — is in
scope and competes on the same score; any routine may add to it) that the routines read
and write, validated by `npm run pipeline` (part of `npm run check`).

```
docs/pipeline/exchange.json          ideas not yet assigned to a venture (parked / promoted / declined)
docs/pipeline/queues/<venture>.json  one queue per venture: status open|finished, scored items
docs/pipeline/queues/new-ventures.json  the exchange's backlog of research spikes for new lines (weight 2;
                                     owner 2026-10-17: new-venture work visible and scheduled, built by idle slots)
```

Item fields: `score` is STRATEGY §5 (evidence × reach ÷ effort), higher first, oldest first on
ties — ranked across queues by **score × the queue's `weight`** (2026-10-11, owner: a new income line
outweighs improving a product that has not earned; STRATEGY §5's table says which queue gets 2, 1 or
0.5, the Sunday review keeps it current, `npm run pipeline` prints it); `proof` is the number that would show it worked; `blocked` items name what they wait on
and do not count as "empty". An item that only needs elapsed time rather than a blocker — a
day-7 or day-30 review — stays `todo` and carries `not_before: YYYY-MM-DD`: `npm run pipeline
next` skips it until that date (listing it on a `scheduled:` line instead) and offers it from
07:00 UTC on that day — after the 06:37/06:52 metrics jobs have written the Daily numbers row a
dated reading is usually dated for (2026-10-08: the midnight burn-down read a "10-08 row" item
against the 10-07 rows); `cold` and `claim` apply the same hour. Like a blocked item it still counts as work, so it does not put the queue into
`needs_research`. **Starvation** (2026-10-01): when no queue is flagged but `next` finds nothing
buildable anywhere — every open item blocked or dated — `npm run pipeline empty` lists the open
queues with no buildable item instead, oldest `updated` first, so the build slot researches the
first of them rather than idling (both slots did nothing on 2026-10-01 morning: `next` null,
`empty` `[]`). One buildable item anywhere ends the fallback. **Doing** (2026-10-05): a `doing` item is one a run is building,
dated by `doing_since` (else `added`); `npm run pipeline` lists every one on a `doing:` line. One that has been doing
for more than a day with no future `not_before` is a cut-off session's leftover (nothing of it reached `main`), so
`next` offers it again; a deliberate hold is `todo` with `not_before` (or carries `not_before` while doing). **Claim** (2026-10-07): the
`doing` edit only guards other sessions once it is on `main`, so a session runs `npm run pipeline claim <venture>/<id>
-- --by=<routine>` right after `next` (the `--` matters: npm keeps a bare `--by=` for itself, 2026-10-08) — one commit of the queue file (`pipeline: claim <venture>/<id> (<routine>)`), pushed
before any work, like the slot marker; a claim refused because another session's `doing` is under a day old means take
`next` again (on 2026-10-07 the 17:00 burn-down and the 17:10 build each built `search-console-api-reading` in full, and the
second push was discarded). The watchdog never counts a claim commit as a slot's trace. **Research first** (2026-10-22, foundry `claim-only-when-buildable`): `next` is null — and the gate claims nothing — while an open queue out of cooling is flagged `needs_research` or empty, because the routines research such a queue before building (the 17:20 build slot had claimed a gankdat item, researched new-ventures, released the claim in the same commit, and the 19:11 slot claimed it again); the status says `research <venture> first — the build waits` and names the item that would follow, `cold` lists the research reason first, and the fallback's capped `next --max-effort` keeps the raw ranking since it never does market research. **Plain Node** (2026-10-12, foundry `claim-before-install`): `next`, `empty` and `status` read the queue code from `packages/core/src/pipeline.ts` through Node's type stripping, so like `cold` and `claim` they run before `npm ci`; the build and burn-down routines claim their first item right after their gate, within a minute of the slot, not after the 5–7 min install that used to precede the first working `next` (the 17:00 and 17:10 slots collided on 10-07 and 10-10 because of it). **Build slot in flight** (2026-10-23, foundry `research-defers-to-build-slot`): the 17:00 build and the 17:00 burn-down read the same research list and research has no claim marker, so `cold` (burn-down only) reads `docs/ops/SLOTS.md`: a `| build | started` line of the last hour with no `| build |` run-log line stamped after it means that slot is researching now, and every research reason (flagged, empty or starved queue) moves into a `(deferred: <venture> research — build slot started HH:MM UTC is in flight)` clause that is not work — buildable items are unaffected (the claim covers them). The burn-down's next hourly fire sees the build's research as cooling, or takes it when the build died. Limit: the burn-down that pulls before the marker lands (~:10) still cannot see it. **Research claim** (2026-11-03, foundry `research-claim-marker`): research now has the same marker as an item. `npm run pipeline claim-research <venture> -- --by=<routine>` (plain Node, before `npm ci`) pushes `researching_since` (the minute, `YYYY-MM-DDTHH:MMZ`) and `researching_by` on the queue in one commit (`pipeline: claim-research <venture> (<routine>)` — never a trace for the watchdog or the slot table, like an item claim); for 2 h the queue is cooling for `next`, `empty`, `cold` and `starved()` (`npm run pipeline` shows it as `research claimed HH:MM UTC by <routine>`), so the other slot's `next` is no longer null for it and its `empty` leaves it out. The claim is refused while another session's is under 2 h old, and while the queue is cooling anyway (researched within 48 h or waiting on `research_after` — research is not due); an older claim is a cut-off session's leftover and is taken over. Two claims can still land in the same minute (each pull saw a clean queue), so a research pass runs `npm run pipeline research-landed <venture> -- --since=<slot start>` before its commit: it fetches `origin/main` and prints `landed: <subject>` (exit 1) when a `<venture>: research …` or `<venture>: exchange pre-research …` commit is there since the slot — the pass is discarded, theirs pulled, one run-log line written — else `clear:`. The research commit sets `researched` and removes both fields. On 2026-11-03 (and 2026-10-22) the 17:00 build and the 17:00 burn-down both researched tax-workbook and pushed at 17:17; the in-flight clause above could not help because the burn-down had pulled before the build's marker, and the build's duplicate pass was discarded in a conflict merge. **Missed exchange** (2026-10-24, foundry `exchange-missed-slot-fallback`): `cold -- --routine=build` prints `exchange missed: <Wednesday> — run docs/routines/exchange.md` as its FIRST reason from Thursday to Saturday (UTC) when no `| exchange |` run-log line and no commit subject ending `(venture exchange)` exists since that Wednesday 08:00 UTC (`missedExchange` in `scripts/pipeline-cold.ts`; the commit subjects come from `git log --since`, the run log alone also counts, so a shallow clone cannot hide a trace); the build routine runs that gate right after its slot marker and, on that reason, runs the week's exchange instead of claiming an item, writing the exchange's own traces plus one `| build |` line for the watchdog. Wednesday 10-21 every Fable slot missed (the allowance week ends Thursday 03:00 UTC, the burn runs Tuesday night to the limit), the W43 exchange never happened and the watchdog only wrote a line; Sunday to Wednesday the next exchange is nearer than the missed one, so the gate is silent. **Cooling** (2026-10-06): a queue carries
`researched: YYYY-MM-DD`, the day of its last research run (every research run sets it with `updated`); for 48 h after
that the starvation fallback skips the queue and `npm run pipeline` lists it on a `cooling:` line, so a venture is not
researched twice in a day (2026-10-05 had five research runs and the next morning's build was offered the same venture
eleven hours later). Since 2026-10-17 (foundry `empty-skips-cooling-queues`) the same 48 h cover a flagged or emptied queue: `empty` and `cold` leave it out until the cooling ends, so the spike that empties a queue the day it was researched does not send the next slot back to it. When `next` is null and every starved queue is cooling, `empty` prints `[]` and the status says
so: the run writes one run-log line and stops (the one exchange pre-research pass per window aside — the burn-down's night from 17:00 UTC, the build's day from 07:00 UTC since 2026-10-10, `npm run pipeline cold [-- --routine=build]` says whether it is spent; since 2026-10-18 (review W42, foundry `pre-research-shelf-cap`) the pass adds one scored spike to `new-ventures.json` when it holds fewer than two open spikes — fewer than three since 2026-11-11 (review W45 §4, foundry `pre-research-shelf-cap-three`: the 11-09 report read burn-down 20 % built over a one-item pipeline) — and is skipped otherwise, instead of parking an exchange idea — a spike is work the next slot builds, a parked idea waits for a Wednesday). A spike is scored only after its sources' terms are read (2026-11-11, foundry `exchange-source-terms-before-scoring`): the exchange's relay round carries, for every source the spike would read, its terms / legal-notice / data-use page and a `RENDER` of any page that answers a plain GET as a shell, the terms line is quoted in the candidate row, and a source whose terms forbid automated access or whose data sits behind an identity-verified account is parked at once with no spike — both 2026-W46 spikes parked within the day on walls two relay lines would have shown. **Waiting** (2026-10-07): a
research run that finds no new evidence — the metrics unchanged since the last pass, every lever built or owner-blocked, the next
signal a dated reading — sets `research_after: YYYY-MM-DD` (that reading's date) instead of adding items; the fallback treats
the queue as cooling until then and the status says `waiting until <date>` (three ventures had each been researched three times
in eight days on an unchanged zero). **Dated within a day** (2026-10-20, foundry `dated-within-day-not-starved`): a queue whose only open items are `todo` with a `not_before` of today (before 07:00 UTC) or tomorrow is waiting, not starved — `starved()`, `empty` and `cold` leave it out, the status shows it on `scheduled:` and says it waits for dated evidence (the 00:07 night slot had researched two ventures whose next item was buildable at 07:00 the same morning). A `finished` queue is a venture
with nothing left to do; only the exchange or the review reopens it. Every change to a queue
lands in the same commit as the work.
