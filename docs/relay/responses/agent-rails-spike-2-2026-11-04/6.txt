# How Seller Services Work

What a seller service is, how to set one up, and how to accept tokens on your own backend.

A **seller service** is a listing on the Skyfire Directory that offers a resource (i.e. MCP server, API, webpage, or  Fetch.ai agent) in exchange for a KYAPay token. As a seller, you configure how restrictive access to that resource is: what identity a buyer agent must disclose, and whether reaching it costs anything at all.

A seller agent publishes and owns each seller service. See [Seller Guide](https://docs.skyfire.xyz/docs/seller-guide) for creating a seller agent.

## The full flow

A seller service follows the same path whether or not it charges for access.

1. A buyer agent discovers your seller service, through the [Skyfire Directory](https://docs.skyfire.xyz/docs/service-discovery) or another channel you point it to.
2. It [creates a token](https://docs.skyfire.xyz/reference/create-token) for your seller service, specifying your service's ID in the request, which addresses the token to your seller agent.
3. It calls your service, passing that token in whichever header your backend expects, `kyapay-token` by convention.
4. Your service reads that header and admits the request once the token checks out.

## Two types of setup

Operating as a seller involves setup on Skyfire, and setup in your own backend.

<Cards columns="2">
  <Card title="Setup on Skyfire" icon="fa-gear">
    Create your seller service and submit it for approval. You do this once, in the dashboard or through the API.
  </Card>

  <Card title="Setup in your backend" icon="fa-server">
    Verify every incoming token, charge it, and deliver. This is code you write, running on your servers.
  </Card>
</Cards>

> Skyfire provides the infrastructure; your backend provides the judgment. Verifying and charging a token is yours to implement, which is what lets you decide what counts as valid access and how much it costs.

## Setup on Skyfire

This assumes you already have a seller agent. See [Seller Guide](https://docs.skyfire.xyz/docs/seller-guide) for creating one.

### Create your seller service

<Tabs>
  <Tab title="Dashboard">
    Click **Create Service**, then fill in the seller service details.


    <Image src="https://files.readme.io/fcb4ebe366ac4cafd287f7513ed5d8ed79a804e48329266ec63bc6955f6f4e73-Screenshot_2025-06-24_at_3.45.04_PM.png" align="center" width="50%" caption="Add your MCP server, OpenAPI spec, or website by filling out the seller service details." />

  </Tab>

  <Tab title="API">
    `POST /api/v1/agents/seller-services` with your seller agent's API key. See [Create Agent's Service](https://docs.skyfire.xyz/reference/create-agents-service) for the full schema.

    ```json
    {
      "name": "Acme Widgets",
      "description": "Widget lookup and purchase for agents",
      "type": "MCP_SERVER_REMOTE",
      "mcpServerUrl": "https://mcp.acme.example/mcp",
      "price": "0.05",
      "priceModel": "PAY_PER_USE",
      "minimumTokenAmount": "0.05",
      "acceptedTokens": ["kya", "kya-pay"]
    }
    ```

    Provide exactly one URL field, matching the type you chose. To list, update, activate, or deactivate a seller service afterward, see [Get Agent's Services](https://docs.skyfire.xyz/reference/get-agents-seller-services-all), [Update Agent's Service](https://docs.skyfire.xyz/reference/update-agents-service), [Activate](https://docs.skyfire.xyz/reference/activate-agents-service), and [Deactivate](https://docs.skyfire.xyz/reference/deactivate-agents-service).
  </Tab>
</Tabs>

One seller agent can publish more than one seller service, each with its own price, accepted token types, and identity requirements.

<Accordion title="What you configure on a seller service">
  | Field                  | Description                                                                                             |
  | ---------------------- | ------------------------------------------------------------------------------------------------------- |
  | Name and description   | Shown publicly in the [Skyfire Directory](https://docs.skyfire.xyz/docs/service-discovery)                                      |
  | Type and URL           | API (OpenAPI spec), website, or MCP server, plus the matching URL                                       |
  | Price and price model  | Per use, per MB, or subscription, or free, if your seller service gates on identity rather than payment |
  | Minimum token amount   | The smallest token you will accept                                                                      |
  | Accepted token types   | Which of `kya`, `pay`, and `kya-pay` a buyer agent can create for it                                    |
  | Maximum token lifetime | The longest expiry a buyer agent can request                                                            |
  | Identity requirements  | What a buyer agent must disclose before transacting                                                     |
  | Terms of service       | A link to your legal terms or usage policy                                                              |

  Each seller service is identified by a unique ID. Buyer agents pass that ID when creating a token, and it appears in the token as the `ssi` claim, which is how you confirm a token was created for your seller service rather than another.
</Accordion>

### Set identity requirements

This step is optional. Without identity requirements, any buyer agent with sufficient funds can transact with your seller service.

To require identity, declare which fields a buyer agent must include in its `kya` or `kya-pay` token, and which kinds of buyer agents you accept: individuals, organizations, or both. See [Identity Fields](https://docs.skyfire.xyz/reference/identity-fields) for the fields you can require, and [Know Your Agent (KYA)](https://docs.skyfire.xyz/docs/kya) for how verification works.

### Submit for approval

Skyfire reviews each seller service before buyer agents can create tokens for it. Review typically takes 48 hours. The review confirms that the seller service works and is configured correctly, so tokens created for it validate as expected once buyer agents start calling. Once approved, your seller service is discoverable in the [Skyfire Directory](https://docs.skyfire.xyz/docs/service-discovery).

## Setup in your backend

A seller service is built to receive a token with every request.

### Assign a token header

KYAPay tokens are standard signed JWTs. The standard is for buyer agents to send them in the `kyapay-token` header, so enforce that header on your service.

> Older integrations, or older buyer agents, may still use the deprecated `skyfire-pay-id` header instead.
>
> Enforce the dedicated `kyapay-token` header rather than reusing the standard `Authorization` header. Many services already use `Authorization` for their own authentication, and reusing it for KYAPay tokens can cause conflicts or unintended behavior.

### Choose an integration path

Choose one of three integration paths below, depending on the level of control and security your service needs.

<Tabs>
  <Tab title="1. Require tokens on every request">
    **Recommended.** Require the agent to include a token (`kya`, `pay`, and/or `kya-pay`) with each request, in the `kyapay-token` header.

    Your service validates the token to authorize the agent, and may support charging flows tied to `pay` or `kya-pay` tokens. This is the simplest and most common integration pattern, and the one covered in [Verify, deliver, and charge](#verify-deliver-and-charge) below.
  </Tab>

  <Tab title="2. Create-account-and-or-login endpoint">
    Use an identity token (`kya` and/or `kya-pay`) to provision or authenticate accounts.

    1. The agent calls your `/create-account-and-or-login` endpoint with a Skyfire identity token in the `kyapay-token` header.
    2. Your service validates the token and extracts the buyer's identity.
    3. You create an account if one does not exist, or log the agent into an existing account.
    4. You return your own session or access token for future requests.
    5. When a purchase is required, the agent provides a `kya-pay` token.

    This model is useful if you maintain persistent accounts or user state.
  </Tab>

  <Tab title="3. Account creation + password">
    An extension of the previous path, adding a password requirement for additional security and flexibility.

    1. The agent calls `/create-account-and-or-login` with a Skyfire identity token.
    2. The agent also provides a password in the request body.
    3. Your service validates the token and extracts the human buyer's identity (for example, `hid.email`).
    4. You create or authenticate the account using your existing CIAM or authentication system.
    5. The `kya` or `kya-pay` token may be exchanged for an internal access token.
    6. The agent logs in with the correct password if the account already exists.

    The human principal behind the agent can also log in directly to your service through this same flow.
  </Tab>
</Tabs>

> Other integration paths may be possible. Contact <support@tryskyfire.com> to discuss your specific use case.

### Verify, deliver, and charge

Whichever path you choose, three steps happen in order once a token reaches your service.

1. **Verify the token.** Confirm it is genuine and addressed to you before doing anything else. See [Verify and Extract Data from Tokens](https://docs.skyfire.xyz/docs/verify-and-extract-data-from-tokens) and [Handling Missing or Invalid Tokens](https://docs.skyfire.xyz/docs/handling-missing-or-invalid-tokens) for how to do so.
2. **Deliver.** Deliver the service, tool, or resource once the token passes verification. Delivering before charging carries no risk of non-payment: creating a `pay` or `kya-pay` token commits the amount against the buyer agent's wallet, and Skyfire guarantees settlement for a valid token. If you never charge it, that hold releases back to the buyer agent, so nothing is lost on either side. See [Payments & Settlement](https://docs.skyfire.xyz/docs/payments-settlement).
3. **Charge the token.** This step applies only if your seller service accepts `pay` or `kya-pay` tokens. Call [Charge Token](https://docs.skyfire.xyz/reference/charge-token) with your seller agent's API key.
   * The token's amount is a maximum, not a fixed charge. Charge what is owed.
   * Partial and repeated charges are allowed, up to the token's value, which suits metered work.
   * A `kya` token carries no value and cannot be charged.
   * You can charge for up to 24 hours after a token expires, provided you validated it before expiry.
     A request may also arrive with no token, an expired token, or one created for a different seller service.
