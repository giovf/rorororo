🎉 Turn USPTO trademark filings into lead data — no login, no API key, one row per application, with the applicant, the mark, the classes and the contact details on the record: correspondent e-mail and phone, attorney, owner address .
Built for IP services, legal and B2B sales to new brands.
🔍 What is USPTO Trademark Leads — and when should you use it? #what-is-uspto-trademark-leads-and-when-should-you-use-it
It answers two questions about the USPTO trademark register, live on every run:
Who filed a trademark application in the last days? New filings mode lists the applications filed in the last 14 days, newest first — optionally only the ones filed without an attorney (pro se), in the classes you care about.
Which applications belong to this owner, or carry this mark? Search mode finds applications anywhere in the register by owner name and/or mark text.
Every result is then read from its own USPTO status page, which is where the contact details are.
Use it when you need: a daily list of new applicants to reach out to; the filings of one company with their contact person; the applications behind a brand name.
Use something else when: you only need to know whether a phrase is already taken (a plain availability check does not need the contact details and is faster elsewhere), or you need company firmographics — this is trademark filings, not a company registry.

📋 Overview #overview
Why teams pick this actor:
✉️ The contact details on the record — correspondent e-mail and phone, attorney, owner address, as they stand at USPTO. In a run of 300 self-filed applications on 6 October 2026, every row had an e-mail and 205 had a phone.
🆕 Fresh filings — a new application shows up one to two days after it is filed (measured 2026-10-06: the filings of 5 October were available on 6 October).
🙋 Pro-se filter — keep only the applicants who filed without an attorney. On 5 October 2026 that was 627 of 1,779 filings.
🔎 Search the register — by owner name and/or mark text, with class and live-mark filters (13.3 million records on 2026-10-06).
🔁 Feeds that do not repeat — with "Only new since last run", a scheduled run delivers each filing once.
💰 Pay per delivered row — no subscription; the run stops at your spending limit and tells you.
✨ Features #features
📰 New filings feed — the last 14 days, or a custom filing-date range, newest first.
🔤 Search — every word of the mark text and/or the owner name must match; results newest first. The matching is USPTO's own: for mark text it can also return a mark that is spelled differently (a search for canopy in class 28 also returned KANOPEO).
#️⃣ Serial lookup — a list or a range of US serial numbers.
🧾 One record shape in every mode — mark, filing date, status, classes, goods and services, owner (name, address, legal entity type), attorney, correspondent contact, link to the USPTO page.

❓ FAQ #faq
Do I need an account, login or API key? No.
Where does the data come from? Two public USPTO sources. The list of applications (who filed what, when) comes from the search service behind USPTO's own trademark search page; the contact details come from each application's TSDR status page. The search service is not a documented API: if it changes or stops answering, the run ends with a message that says so, and what was delivered is kept.
What do I search by? Mark text, owner name, international class, filer type (with or without attorney), filing date — or serial numbers.
How current is the data? Every run reads the sources live. A new application appears one to two days after it is filed.
Why does a run take a while? Each lead's contact details are read from its own status page with a pause of at least 2.5 seconds, to stay polite to the official source: about 100 leads per 5-6 minutes.
Does "Only new since last run" skip anything when a run stops early? No. The Actor remembers the filings it has delivered, per set of filters, and looks back 14 days on every run; whatever a run did not get to comes with the next one.
Can a lead come twice? The memory is written while the run goes (every 10 leads) and when the run ends, so a run that stops at maxResults or on a time or spending limit does not repeat its leads. An aborted run writes its memory too when Apify gives it the chance (a graceful abort). If a run is killed without warning — an immediate abort, a crash — the next run can deliver up to 10 of its last leads once more.
Can two runs of the same feed run at the same time? No, and the Actor prevents it, because both would deliver the same leads. A run with "Only new since last run" that starts while another run with the same filters is still going ends at once with a status message; it delivers nothing and does not contact USPTO. Feeds with different filters do not affect each other.
Can I export to CSV / Excel / JSON? Yes — directly from the Apify dataset.
🐛 Troubleshooting #troubleshooting
Fewer rows than expected — raise maxResults , or widen the filters. In search mode every word you type must be in the mark or the owner name.
No rows for the newest day — filings appear one to two days after they are filed, so the newest day in the window is usually empty.
The run ended with "stopped because the maximum charge … was reached" — the run's maximum charge, or what is left of your monthly usage limit, covered fewer leads than you asked for. The dataset holds the ones that were delivered; raise the limit and run again for the rest.
The run ended with "USPTO's trademark search service … " — the search service did not answer this time. Nothing is wrong with your input; run again later. Serial number modes do not use the search service.
The run ended with "another run of this same feed is in progress" — two runs with "Only new since last run" and the same filters overlapped: the earlier one was still going, or had been killed less than three minutes before. Nothing was delivered. Start the run again when the other one has finished; if a schedule causes it, make the interval longer than a run takes, or lower maxResults .
A mark-text search returned a mark without my word — USPTO's index does the matching and also returns some marks that are spelled differently (for example KANOPEO for canopy ). Filter the dataset on markText if you need the literal word.
An application is missing its e-mail — the record has none: the Actor returns what the USPTO status page shows.
⚖️ Is it legal to scrape this data? #is-it-legal-to-scrape-this-data
This actor reads the public USPTO trademark database. Results can still contain personal data (e.g. a person’s name); personal data is protected by the GDPR and similar laws, so only process it with a legitimate basis. A run that the platform starts again no longer writes past maxResults or repeats rows. Apify can move a run to another server while it is going; the Actor then starts again with the same dataset. Until now it started counting from zero: a run with maxResults 30 that was started again after 14 rows ended with 44 rows, 4 of them written twice. The Actor now first reads what its own dataset already holds — those leads count towards maxResults and are not written again. All four modes.
No output field changed, no pricing change.
0.1.11 — 2026-10-07 — fresh filings again, and search by mark text or owner name #0111-2026-10-07-fresh-filings-again-and-search-by-mark-text-or-owner-name
New filings mode returns new filings again. Since about 20 July 2026 it had been returning the same filings of that date as "the freshest": USPTO changed how it numbers applications (a new 50… series since 18 July 2026, and 99… numbers no longer in filing order), and the Actor found new filings by walking down from the highest serial number. It now gets the list of applications by filing date from USPTO's search service and reads the contact details from each application's status page as before. Behaviour change — onlyNewSinceLastRun : the Actor now remembers the filings it has delivered (per set of filters) and looks back 14 days on every run. Each filing is delivered once; whatever a run does not get to (Max results, a time limit, your spending limit) comes with the next run. The first runs of a new feed therefore work back through the last 14 days before they are down to only the newest filings.
onlyNewSinceLastRun — the memory is written while the run goes (every 10 leads), when it ends and on a graceful abort. A run that is killed without warning can repeat at most its last 10 leads in the next run.
onlyNewSinceLastRun — one run per feed at a time. A run that starts while another run with the same filters is still going ends at once with a status message, without delivering anything or contacting USPTO: two at once would deliver the same leads twice.
Behaviour change — pro-se filter: it is applied when the list is made, so the run no longer spends requests on applications that have an attorney.
If USPTO's search service does not answer, the run ends with a message that says so; rows already delivered are kept. Serial number modes do not use it.
serialFrom / serialTo accept the 50… series.

0.1.9 — 2026-10-07 — a run that is cut short stops cleanly, says why, and the next one carries on #019-2026-10-07-a-run-that-is-cut-short-stops-cleanly-says-why-and-the-next-one-carries-on
A run that reaches its maximum charge now stops by itself and tells you. The maximum charge is the limit you set for the run, or else what is left of your monthly usage limit. Until now the Actor did not look at it: the scan went on, leads past the limit were logged as pushed but left out of the dataset, and a longer run was aborted by Apify. The Actor now checks the room left before every USPTO request, stops the scan when there is none, and finishes as a normal run with a status message that says how many leads were delivered.
onlyNewSinceLastRun : a cut-short run no longer loses the rest of its batch. A run that stops early — at maxResults , on a time limit, or on its maximum charge — saves the part it did not reach, and the next incremental run continues with it after the new filings. Nothing is skipped and nothing is delivered twice. Before, the rest of that batch was never delivered. For a daily feed whose maxResults is smaller than the day's filings this means a run can now also return filings older than the previous run's newest one.
The time limits hold. The Actor stops 30 seconds before the run timeout instead of being cut off by it, and maxRunSeconds also covers the first step, locating the newest filing.
Every run ends with a status message that says what was delivered and, for a partial run, why it stopped.
No output field changed, no pricing change.
